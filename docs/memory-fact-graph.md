# Fact relationship graph and source evidence

[English](memory-fact-graph.md) | [简体中文](memory-fact-graph.zh-CN.md)

Open **记忆检索 · 原型** in the sidebar (`#/memory`) and use its fact-graph section. The graph is part of stage three: it connects people, events, objects and places to the exact chapter passages supporting a relationship. It does not implement an embedded Agent or complete stage-two chapter persistence.

## Use the graph

1. Select the private demo or an actual novel and set the last disclosed chapter. Actual novels use committed text; save Writer edits before returning to Memory Lab.
2. Select **添加关系**, choose a disclosed chapter and copy an exact excerpt into the form. Add it with **加入依据**, then enter an entity type and source-grounded name for each endpoint and a relationship label. New manual relationships are recorded as explicit statements; use them only where the source directly supports the relationship. Multiple excerpts can support the same relationship. The selected retrieval evidence can also open this form with its anchor filled in.
3. Select an edge in the Cytoscape.js canvas or its equivalent relation-list entry. The evidence panel shows every supporting chapter, its current revision, UTF-16 source range and exact quote.
4. Review, edit, delete or confirm a relationship. Author confirmation is a separate review state and does not replace the original basis or model/author origin. Editing a relationship clears its confirmation and retains its original basis and origin.
5. Search the eligible graph for a name, relationship or source phrase to revisit distant connections and foreshadowing. Search applies before the display limit, so a relationship outside the initial canvas can still be found.

The canvas and relation list use the same filtered relationships. Their nodes come from those relationships, not from a global catalog of every identity in the novel. Names must occur literally in the attached quotes. Nodes are identified by entity type and exact name; the prototype does not resolve same-name people, aliases or identity changes automatically.

## What the labels mean

| Label | Meaning |
| --- | --- |
| Explicit source statement | The relationship is annotated as directly stated by the cited text. This is a classification, not a proof generated by the application. A model-created explicit relationship remains visibly marked as model-proposed and unverified. |
| Inference | The relationship is a model-proposed interpretation of the cited text. Editing or confirming it does not change its original inference basis or model origin. |
| Author confirmed | The author has explicitly reviewed the relationship. The original explicit/inferred basis and model/author origin remain recorded. Confirmation cannot make a stale or future source eligible. |

Exact quotation checks establish where the supporting words came from. They do not establish that a predicate, entity type or inference is correct. Authors must review relationship labels and avoid entering a later secret into an annotation attached to an earlier passage. Models can also produce incorrect interpretations; the graph never treats a model's “explicit” classification as independent verification.

## Revision and disclosure contract

An evidence anchor records the project, stable chapter identity, SHA-256 revision of the title and plain-text body, UTF-16 start/end positions and exact quote. The chapter's current position in the chapter list defines its disclosure order.

A relationship is eligible only when **all** its evidence anchors match the current committed project and chapter revisions, match the exact source ranges and fall within the selected chapter cutoff. A multi-premise inference cannot appear early merely because its first premise occurs in an early chapter. Reordering chapters changes the boundary immediately; deleting a chapter removes its relationships from the visible graph. If the selected cutoff chapter is deleted from the same project, refreshing clears that selection. The graph and retrieval remain unavailable until the author explicitly selects a new cutoff; further refreshes cannot silently choose a later chapter.

Changing a source chapter's title or body invalidates every relationship anchored to that chapter, including author-confirmed relationships. The prototype keeps the stored annotation but hides the whole relationship; it does not transplant old quotes to a new revision, partially retain an inference or silently re-extract it. Create a new relationship from the current source after reviewing the revision. Revisions are content hashes: restoring exactly the same title and body can make an existing anchor valid again. The evidence panel is a current-source view, not a historical chapter-version browser.

Project/source/cutoff changes clear outdated visible selections and pending proposals. Before a model request, only selected, validated, disclosed source excerpts are eligible. Late responses cannot restore facts from a superseded source or disclosure boundary. Future relationships, their node labels and their stored counts are not exposed through the visible graph.

These checks apply to the fact graph and its extraction requests. Existing Writer generation prompts, `writing_search`, character settings and whole-book summaries do not automatically inherit this contract.

## Optional model proposals

Model extraction is an explicit action using the active generation API configuration, including its output/thinking budget. It is independent of Memory Lab's embedding/reranking controls. Manual graph creation does not require a model or an API key.

The request includes only the selected source quotes and instructions for returning relationships; it does not include whole chapters, chapter titles, novel metadata, the existing graph, MCP results, Skills or an Agent context. At most eight excerpts, 8,000 total selected UTF-16 characters and 16 proposed relationships are accepted per extraction. Each excerpt is limited to 2,000 UTF-16 characters. The request has a 60-second timeout and can be cancelled.

The application validates the response shape, entity types, source references and source-grounded endpoint names. It assigns the actual project/chapter/revision/range anchors; the model cannot supply replacement source identities. Malformed responses are rejected. All proposals start unconfirmed and require an explicit save to become persisted graph annotations. Extracting proposals alone does not save them or confirm them.

This is bounded extraction from selected evidence, not unattended whole-novel graph building. It can miss relationships or return wrong classifications. Automated tests use deterministic model responses and establish request/validation boundaries, not real-model extraction quality.

## Persistence and limits

Relationships are saved separately from novel content in project-scoped IndexedDB records. Writes compare the last-read graph version in the same transaction as the update. Concurrent changes fail explicitly instead of overwriting the newer graph. Storage errors or malformed stored data are reported; loading an invalid record does not silently replace it with an empty graph.

Actual-novel graph annotations are **included in Settings → Data management → Export all data / Novel data** and restored with their novels. This preserves the complete stored graph, including stale or undisclosed relations, without changing evidence revisions or provenance; source/disclosure checks still apply after restoration. Plain manuscript exports are not backups. The private memory demo is excluded. Resetting that demo leaves its existing graph annotations stored. There is still no stale-annotation cleanup interface. See [backup behavior, mobile navigation and acceptance](graph-backup-mobile.md).

| Boundary | Limit or behavior |
| --- | --- |
| Saved relationships | 10,000 per project |
| Evidence per relationship | Up to eight anchors, each at most 2,000 UTF-16 characters |
| Saved evidence/document | At most 8 million quoted UTF-16 characters and 24 million serialized UTF-16 characters per project |
| Visible relationships | Up to 200 after source, cutoff and search filtering |
| Graph search | Searches the full eligible bounded graph before applying the display limit |
| Model extraction | At most eight excerpts / 8,000 selected UTF-16 characters / 16 proposals per request |
| Entity identities | Type plus exact source name; no cross-alias identity resolution |

The display cap bounds canvas work; it is not evidence that arbitrary whole-book graphs render at once. Existing retrieval pressure measurements in [long-novel tests](memory-stress-tests.md) measure that retrieval subsystem, not graph extraction or layout throughput.

## Acceptance checks

- **Edit an old chapter:** create and confirm a relationship, edit any part of its source chapter and save. Return to the graph and refresh its source. The old relation, nodes that exist only through that relation and its evidence must disappear. A new relationship must bind to the new revision.
- **Find foreshadowing:** link an early object or event to its cited passage, then search for its name or relationship with a later cutoff. The result must retain the early chapter and exact quote. This is source-backed recall of an annotation, not automatic proof of foreshadowing.
- **Prevent future disclosure:** save a later identity relation and an inference supported by both early and late passages. Before the later chapter, neither relationship nor its future-only node name may appear. Moving the cutoff backwards must also clear a selected future relationship and reject late model proposals.

The core regression uses a synthetic long novel with relationships stored in reverse chapter order. It checks exact evidence, source edits, reordering, future-only nodes and finding a chapter-one clue after thousands of later relationships, writing `artifacts/memory-fact-graph/core.json`. The storage suite covers persistence failures and concurrent version checks; extraction tests exercise source-only requests and invalid model outputs.

The **2026-10-04** local [core record](testing/memory-fact-graph-2026-10-04/core.json) and [source/validation provenance](testing/memory-fact-graph-2026-10-04/provenance.json) retain this single synthetic run:

| Recorded item | Result |
| --- | --- |
| Fixture | 600 chapters / 1,411,959 UTF-16 characters / 5,400 relationships |
| Source checks | Ten groups / 241 exact-evidence checks |
| Network requests | Zero |
| Local validation | 72 smoke suites, strict lint and production build passed |

This is one local run in a shared environment, not a comparative performance benchmark or external-model evaluation. Selector timings do not measure browser layout. Browser validation is reported separately by CI.

Run these regressions, then build before the browser check:

```bash
npm run smoke:memory-fact-graph
npm run smoke:memory-fact-store
npm run smoke:memory-fact-extraction
npm run build
npm run test:browser-memory-fact-graph
```

Use the current revision's CI result for pass/fail status; prior retrieval benchmarks do not certify the graph. The 14 configured graph browser scenarios cover genuine canvas edge clicks and keyboard list selection, exact evidence, confirmation/reload, author editing, source and cutoff invalidation, deleted-cutoff recovery requiring an explicit selection, multi-premise clues, model proposal review, malformed/late responses, empty novels and dark/mobile layouts. Six explicitly requested synthetic model calls test the provider boundary. Browser checks use the built application and a local synthetic provider, not a paid model. Screenshots, the request audit and results are written to `artifacts/browser-memory-fact-graph/`.

## Open-source component

[Cytoscape.js](https://github.com/cytoscape/cytoscape.js) is pinned to **3.34.3**, under the MIT license, without modifications to upstream source. Its license notice is distributed in `public/licenses/`. It supplies graph rendering and interaction; source validation, persistence, review provenance and extraction limits are application code. The existing mind map continues to use mind-elixir.
